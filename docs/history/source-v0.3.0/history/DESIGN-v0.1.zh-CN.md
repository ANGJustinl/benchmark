# ChangeBench：实验设计 v0.1

## 1. 研究对象

我们测量的不是“代码是否像优秀开源项目”，而是：**在相同模型、工具和资源条件下，加入设计指导是否改善初版工件，并使统一维护者以更低代价完成合理的后续修改。**

这是初版设计策略的工件效应，不是某个完整开发框架的端到端生产效率。规划、并行 Agent、持久记忆和自动发布等机制不在本次实验中。

研究问题分为两项：A 对 B 检验新增设计原则是否有用；B 对 C 检验在这套固定运行环境中，按需加载是否比常驻同一内容更合适。不能从 B/C 的结果直接推断所有原生客户端的 Skill 加载效果。

## 2. 对照条件

| 组别 | 初版开发者接收的内容 |
|---|---|
| A | 项目事实、公开需求、已有代码、真实验证义务 |
| B | A 加上常驻的设计判断正文 |
| C | A 加上 Skill 元数据；正文只在 `read_skill` 调用后进入上下文 |

B/C 的设计正文只有一个源码来源：`changebench/policy.py`，导出文件和测试核对其内容。Skill 的触发介绍与调用开销本身属于 C 的处理效应，不谎称两组总提示完全相同。C 即使没有触发也保留在原分组，不以“是否听话”筛掉样本。

维护者始终使用 A 的中性指导，不继承初版开发者的实验性 `AGENTS.md`、Skill 或对话历史。自然形成的项目说明、决策记录、代码和测试则保留，它们也是工件的一部分。每个阶段启动全新工作进程和会话。

## 3. 一个实验单元

```text
初始任务 T0 → 冻结初版快照
                  ├→ 冷启动维护者 → 局部调整 L → 旧契约 + 新契约
                  └→ 冷启动维护者 → 真实扩展 E → 旧契约 + 新契约
```

两条后续需求在 T0 时都不公开，且互相不可见。它们不是先后串行执行，避免先发生的扩展改变第二次修改的起点。初版失败时两条维护分支标记为 blocked，仍留在原定实验分母中。

初版的隐藏评测结果不提供错误样例或预期答案给后续维护者。维护者仅获得新需求和工件。模型可以自行添加、运行公开测试，但声明“已通过”不会代替独立验收。

## 4. 任务集

| 任务 | 起点 | T0 | 局部分支 | 扩展分支 |
|---|---|---|---|---|
| config | 空项目 | TOML 配置与验证 | 环境变量覆盖 | 命名配置组合 |
| records | 空项目 | CSV 解析、过滤与汇总 | 稳定排序 | JSONL 输入 |
| pricing | 旧代码 | 金额计算与验证 | 折扣上限 | 扣库存时的完整性 |
| delivery | 空项目 | 单通知提供方 | 有条件重试 | 第二提供方的不同契约 |
| inventory | 空项目 | 幂等预留 | 释放与复用 | 批量原子提交／回滚 |
| reports | 旧代码 | 保持旧导出契约 | 排序 | 新版本格式与旧版兼容 |

任务的详细可执行契约位于 `catalog.py`。隐藏测试含手写边界值和固定种子的随机输入；两个后续阶段保留完全相同的 T0 回归集。T0 的公开测试只有允许示例，隐藏样例和其他未来分支不进入工作区。

为消除依赖安装的干扰，这版采用 TOML 而不是早先示例中的 YAML，并统一 JSON-lines 进出、只允许标准库。内部可以用函数、模块或类，没有规定分层。通知提供方是确定性响应模拟；库存任务验证的是状态机与原子性语义，不是实际数据库并发、进程隔离或持久化恢复。

这些是可审查的微型工程任务，不是 NoneBot2 规模的仓库测试。限制标准库也意味着它不能衡量依赖选型、复杂框架集成或真实部署能力。应先检查强模型是否出现接近满分的天花板效应，再决定是否扩展任务规模。

## 5. 指标与分母

主要结果分别报告：初版正确率、局部分支完整成功率、扩展分支完整成功率。后两者要求初版和对应分支的新旧契约全部通过。两分支同时成功只作为更严格的辅助结果。

成本保留原始 input/output tokens、缓存／推理子项、工具调用和阶段墙钟时间。不把 Token、正确率与主观结构评价混成一个总分。代码行数、文件数和修改文件数仅作为诊断，不直接奖励或扣分。

设每条轨迹的开发成本为 C0，局部维护成本为 CL，扩展维护成本为 CE。预先设定的等权场景成本为：

`C_lifecycle = C0 + 0.5 × CL + 0.5 × CE`

实际实验消耗则为 `C0 + CL + CE`，两者不可混淆。等权仅是当前任务分布的明确假设，不代表所有真实项目。应同时查看两个分支，避免某一方向的收益掩盖另一方向的退化。

“每个成功场景的成本”使用全部尝试的加权成本除以成功场景的加权数量，包括失败尝试已经花掉的成本；没有成功时结果为 null。未调用的 blocked 阶段没有执行成本；已调用但用量未知的阶段则必须为 null，二者不能混为一谈。缓存 Token 已包含在 input 中，推理 Token 已包含在 output 中，不重复加总。

基础设施故障单独报告，相应模型成功率不被伪装成有效估计。结果缺项、重复项、计划哈希不一致、源码漂移和缓存成功字段与阶段证据不一致均拒绝汇总。

## 6. 统计设计

初始计划为六个任务族 × 三组 × 两次独立开发，共 36 条轨迹、最多 108 次阶段调用。任务与重复构成配对区块，组别顺序随机；同一区块使用相同验收种子和相同公开需求。

生成种子与隐藏验收种子分离。当前 Responses 工作进程不声称能够固定模型随机种子，而明确记录 `seed_supported=false`。模型 ID、推理配置摘要、配置哈希、源码哈希、运行镜像 ID 和实际 API 使用量保留在审计记录中。

实现了按任务族重采样的配对 bootstrap，用于探索性差异区间；不把分支、测试用例或两次重复视为新的独立任务族。六个任务族不足以支撑普遍结论，零宽区间也不意味着已证实等价。本次夹具回放不生成 A/B/C 推断区间。

## 7. 结构审查

盲审只要求具体代码证据：哪里出现了对当前任务无价值的间接层，哪里有独立职责被迫一起理解或修改，跨文件变更到底是契约要求还是无关扩散。允许“无法判断”，不要求发现问题，也不按 Repository、接口或文件数量自动判错。

导出的匿名包附当前需求，并生成 A/B、B/C 的随机左右顺序配对表。实验标签映射保存在控制端。代码风格或注释仍可能透露偏好，因此只是隐藏组别标签，不保证绝对盲法。评审尚未由第二位独立评审者实际完成。

## 8. 先验证评测器，再评价模型

校准包括：不同文件布局的正确实现应都通过；初版不修改应不能通过新增需求；新功能伴随旧行为破坏应失败；人为植入的语义错误应被拒绝；伪造通过声明、空输出、无效 JSON、重复 JSON 键、无限循环和输出洪泛都不能成为成功。

两种正确布局复用了同一套参考业务逻辑，不是两个独立作者的参考实现。用例与参考代码也来自同一轮实施，仍可能存在共同误读。因此这些测试建立的是工程可运行性与部分判别力，不是构念效度或外部效度的完整证明。

## 9. 决策规则

v0.1 不自动宣布胜者。先检查环境与用量完整、模型版本一致、无数据泄漏，再看 B 是否在成功率不明显受损的情况下减小后续成本，以及 C 的按需机制是否产生额外净收益。若结果不稳定或三组接近，不应增加 Skill。

用于实际决策前，还需要真实 API/Docker 联调、小规模模型试跑、私有未公开任务复验；若任务过于简单，应增加真实代码库与跨模块变化，而不是继续增加主观评分项。

新增机制的目标依然是可删除：若更简单的 A 已经足够好，结论就应是保留 A。

## 关于整体重写

维护者可以重构，不能为了保护某种架构而强制保留代码。但如果它通过整体重写一个小程序迅速通过测试，应解释为“这个任务的重写成本低”，而不是“初版架构优良”。可结合前后快照与差异诊断识别这种情况。若整体重写普遍发生且成本很低，优先扩大任务的真实状态、兼容性和集成约束，而不是增加强制代码保留比例或主观复杂度扣分。
